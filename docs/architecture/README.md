# Architecture

A TypeScript modular monolith in a pnpm workspace. The built web app and backend run as one local Node.js application.

| Part              | Current choice                                                     |
| ----------------- | ------------------------------------------------------------------ |
| Web app           | React, Vite, Tailwind, small reusable UI components                |
| Backend           | Fastify with native Ajv validation                                 |
| Contracts         | Shared TypeBox schemas and inferred types                          |
| HTTP client       | OpenAPI generated from routes; fetch client generated by Orval     |
| Agent integration | Official MCP SDK, local Streamable HTTP endpoint                   |
| Agent messaging   | Codex Desktop queue/history; shared App Server; Claude Desktop mod |
| Storage           | Versioned JSON file with serialized atomic writes                  |
| Verification      | Vitest and Playwright                                              |

Both apps organize domain code under `features/`. `packages/contracts` owns the handwritten schemas; `packages/api-client` owns generated HTTP code. The client generates its own types, while browser form validation imports contracts directly.

The MVP uses one loopback server per data directory, with no database or user accounts. [Repository details](../../README.md#repository-layout) cover layout and development commands.

The store generates collision-checked eight-character IDs for activities, workspaces, and message markers. Workspace and message `shortId` aliases are immutable; canonical UUIDs and activity Work Keys stay internal for compatibility. Workspace lookups accept either form and normalize references before writes and retry comparisons. Activity updates resolve an existing Work ID or Work Key; titles stay immutable and changed reports append numbered snapshots in the same atomic write. Optional creation request IDs deduplicate retries without overwriting newer versions. The scoped versions endpoint serves the comparison dialog. Version 1 and 2 data is backed up and migrated to version 3 with stable item/message relationships and aliases for old Work IDs; allocating display aliases does not add activity revisions. Both short and legacy UUID message markers can resolve receipts.

Messaging receipts and activity-to-session bindings live in the same atomic file store. Provider connections are lazy and kept separate from explicit work statuses. Desktop discovery uses a stdio Codex App Server strictly for saved metadata/history reads. Sends execute `codex queue` without a shell or `--resume`; Desktop owns execution. Pending receipts are reconciled from a unique input marker and its exact turn, on conversation reads. The open dialog polls pending Desktop receipts every two seconds; there is no background chat-history polling after it closes. Receipt checks share in-flight work and only persist changes.

Claude Desktop sessions are reached through a Claude Code mod that the user installs from Agents. It polls a loopback endpoint with a per-registration token. The store keeps each waiting message in `sending` and hands it out once with a compare-and-set to `queued`, so concurrent polls and server restarts never duplicate a delivery. The mod reports the turn's start and final answer; Congruence never reads the Claude transcript. The registry of polling sessions is in memory and rebuilds within one poll after a restart.

Activity reports may include an exact `agentTarget` to bind an unlinked item at publication. Codex reporters read their current `CODEX_THREAD_ID`; Claude Desktop reporters need no target, because their `desktopSession` also routes messages. The MCP connection identifier and repository name are never treated as chat identity. Existing destinations survive subsequent reports, including reports without a target. The message dialog presents the linked session directly and only exposes the picker for an explicit change or an unlinked item.

Activity cards also open native desktop sessions through fixed, provider-specific URL templates. A Codex Desktop target directly supplies its chat ID; Claude requires a separate optional `desktopSession` with the verified native `local_...` ID. Desktop references persist across reports, but changing a messaging destination clears them. A report from the previous target cannot restore its old desktop reference. Links do not depend on messaging settings, launch a CLI process, or submit a prompt.

Shared Codex sessions use an existing loopback runtime or configured control socket. Stored message changes use the existing dashboard SSE connection. Delivery uses idempotent message IDs and does not automatically resend uncertain work.

Workspace dashboards have their own runtime and command services under `features/dashboards`. MCP returns source directories inside the server data directory. Publishing bundles React and optional Node/TypeScript backend code with esbuild, then activates an immutable version. The previous release remains available when a build fails. Frontend refresh selects the published version, independent of core web builds. Node workers keep backend startup/collection work alive without a browser and are managed by the runtime.

The host renders dashboard bundles in an iframe with scripts enabled and same-origin access disabled. A version-scoped postMessage bridge exposes data reads and command review, never execution. The host validates the sending frame and version; the API rejects opaque-origin requests to command controls. Published static assets alone allow the frame's opaque origin. Backends execute as trusted local Node code, not in a security sandbox.

Command previews freeze resolved data, prompt, destination, and version. Confirmation deduplicates by preview ID and persists a run before execution. A later publication invalidates unexecuted previews. Prepared native-chat runs carry a public correlation marker and no invented session ID; linking uses the agent-reported actual native ID after the human sends the prompt. Command history survives browser closure and restarts, with interrupted execution reported rather than replayed.
